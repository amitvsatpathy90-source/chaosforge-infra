## ADR-0401 — One-way chaosforge → rpe dependency via plain security-group variable

**Status:** ACCEPTED

### Context
chaosforge's execution-service and RPE's detection service need a mutual security-group rule
for the steady-state-probe path: egress on chaosforge's execution-service SG, ingress on RPE's
detection SG, both declared together in `chaosforge/security-groups.tf`. An earlier design had
each Terraform root read the other's SG ID via `terraform_remote_state` — `rpe/` reading
chaosforge's execution-service SG output, `chaosforge/` reading rpe's detection SG output —
leaving the two roots mutually dependent with no valid first-apply order from a clean account.

### Decision
`chaosforge/` takes RPE's detection security-group ID as a plain Terraform variable instead of
via `terraform_remote_state`; `rpe/` reads nothing from `chaosforge/`'s state. The dependency is
therefore strictly one-way (`chaosforge/` → `rpe/`), fixing apply order to `foundation` → `rpe`
→ `chaosforge`.

### Alternatives Considered
- **Mutual `terraform_remote_state` reads (both roots consuming each other's outputs)** —
  rejected: created a circular dependency with no valid first-apply order from clean state.
- **One-sided plain variable with the reverse remote-state read left in place** — rejected:
  switching only one side to a plain variable did not by itself break the cycle; the reverse
  read (`rpe/` consuming chaosforge's state) had to be removed too.

### Consequences
**Positive:**
- Apply order is now fixed and documented (`foundation` → `rpe` → `chaosforge`) instead of
  arbitrary/alphabetical, and each root (`foundation/`, `chaosforge/`, `rpe/`) keeps its own
  state file so a bad apply in one can't corrupt another.

**Negative:**
- `rpe/` must exist and have been applied at least once before `chaosforge/` can apply — a hard
  ordering constraint that didn't exist (in principle, though not in a workable form) under the
  mutual-remote-state design.
