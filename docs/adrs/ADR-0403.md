## ADR-0403 — RPE database credentials follow compose parity, not per-service roles

**Status:** ACCEPTED

### Context
Module 5 provisioned four per-service Postgres passwords (`detection`/`relay`/`alert`/`triage`),
mirroring the per-service `DB_USER` defaults (`detection_role` etc.) implied by RPE's
`application.yml` files. Checking against RPE's own deployment topologies showed those roles are
a CNPG/Kubernetes-only construct, created by `deploy/k8s/db/` bootstrap manifests that don't exist
outside Kubernetes. RPE's own canonical **container** topology
(`deploy/docker-compose.services.yml`, e2e-verified by the project itself) runs all four services
as a single `DB_USER=rpe` login against one `POSTGRES_PASSWORD` — this ECS deployment is a
container topology without CNPG, not a Kubernetes one.

### Decision
All four RPE services (`detection`/`relay`/`alert`/`triage`) authenticate to Postgres as the
single `rpe` user, sharing one SSM-stored password (`aws_ssm_parameter.postgres_password`,
`rpe/secrets.tf`) — matching RPE's proven compose topology instead of fabricating the k8s-only
per-service roles. This also removes Module 5's "manual `CREATE ROLE` bootstrap SQL" gap entirely,
since there is nothing left to bootstrap.

### Alternatives Considered
- **Keep Module 5's four per-service passwords/roles** — rejected: those roles are created by
  `deploy/k8s/db/` CNPG bootstrap manifests that have no equivalent in this ECS/compose-parity
  topology; provisioning the passwords without the roles that back them would have been
  security theater, not real per-service isolation.
- **Write new bootstrap SQL to create the per-service roles for ECS** — rejected: RPE's own
  container topology has never run this way and is the artifact actually proven end-to-end
  (Stage 5); inventing a third, ECS-only credential model outside both of RPE's own topologies
  would be new surface with no precedent to validate it against.

### Consequences
**Positive:**
- Matches RPE's own tested container topology exactly, and eliminates a bootstrap step (per-role
  `CREATE ROLE` SQL) that Module 5 had never actually implemented.

**Negative:**
- All four services share one Postgres login — a compromise of any single service's credential
  compromises DB access for all four. The per-service-role hardening remains real, but only in the
  k8s/CNPG topology where the roles are actually created; it is not silently dropped, just not
  reachable from this deployment.
